# Author an AgentExpress Workflow

## Overview

Turns a described use case into a running AgentExpress deployment. It opens by scoring the
customer's brief against a ten-item readiness checklist and asking for whatever is missing,
because a vague brief does not fail — it produces something confidently wrong. Then it
writes only the four surfaces a customer owns: `app/workflow.json`, `app/subagents/<id>/`,
`app/tools/<name>/` and `kb_docs/<corpus>/`. Everything else — IaC, Gateway targets,
Cedar policies, guardrails, IAM, the UI, the graph — is generated by the framework from
that config and MUST NOT be edited, because a hand-written version is either regenerated
over or left to disagree with the config that produced its neighbours.

Use this when a customer wants their own domain running on the framework rather than the
shipped AWS-architecture sample.

**Editing a bundle exported from the console instead?** Skip steps 0 and 3. Read the bundle,
make the change the user asks for in its `workflow`, `prompts` or `toolCode` (shapes in
[references/contract.md](references/contract.md), "The console bundle"), keep `{"library": …}`
entries and add no secrets, and save it as valid JSON. The user imports it with **Project →
Import a file… → Into this build**; the console's Problems list then checks it with the same
rules as a deploy. To deploy it from a checkout instead, run
`python3 scaffold.py apply <bundle> --exact` and continue from step 8. On that path `pytest`
also checks the shipped sample's own conventions (`$schema`, key order, the sample's agents)
and some of those tests fail on a console bundle that deploys fine, so prove it with
`cdk synth` from `orchestrator/cdk` or `terraform validate` from `orchestrator/terraform`
and report the pytest failures as sample-convention checks rather than fixing the bundle to
match the sample.

## Parameters

- **use_case_description** (required): What the workflow should accomplish, in prose. Example: "Settle household insurance claims: read the FNOL, check the policy wording, price the repair, and produce a settlement decision a human approves."
- **domain_vocabulary** (required): The customer's own names for the things produced, as a list. These become `produces` values and `assetType` strings. Example: "fnol-summary, coverage-finding, repair-estimate, settlement-decision".
- **data_sources** (optional): Each system the agents must read, with how it is reached — a Bedrock Knowledge Base corpus, an MCP endpoint URL, an OpenAPI spec, or a Lambda function. Example: "policy wordings as KB docs; claims history via MCP at https://…/mcp; parts pricing via a Lambda we will write".
- **review_points** (optional, default: "one gate before the final deliverable"): Where a human must approve, revise or deny.
- **workspace_root** (optional, default: the repository root): The AgentExpress checkout to modify.

**Constraints for parameter acquisition:**
- If all required parameters are already provided, You MUST proceed to the Steps
- If any required parameters are missing, You MUST ask for them before proceeding
- When asking for parameters, You MUST request all parameters in a single prompt
- When asking for parameters, You MUST use the exact parameter names as defined
- You MUST support multiple input methods including:
  - Direct input: the description typed into chat
  - File path: a requirements document in the workspace
  - URL: a link to an internal design document
- You MUST use appropriate tools to access content
- You MUST confirm successful acquisition before proceeding
- You MUST treat these parameters as the ENTRY POINT and not as the requirement set, because they are deliberately coarse — step 0 scores them against the ten-item checklist and asks for whatever they did not cover. Having every parameter filled in does not mean the brief is buildable

## Steps

### 0. Check the brief against the readiness checklist

Score what the customer gave you against the ten things the framework needs, ask once for
what is missing, and restate the whole set before designing anything.

**Constraints:**
- You MUST read [references/checklist.md](references/checklist.md) and score the brief against all ten items, marking each **answered**, **missing**, or **too vague to build from**
- You MUST judge an item answered only when the design can be written from it WITHOUT a guess, using the not-enough/enough table in that file, because `use_case_description` is free prose and "build me a claims system" satisfies the parameter check while supplying almost nothing
- You MUST show the customer the scored checklist — all ten items with their status — before asking anything, because it tells them what the framework needs and how close they already are, and a bare list of questions does neither
- You MUST ask for every gap in items 1 to 8 in ONE message, grouped and numbered, because a question at a time turns a five-minute conversation into twenty and they lose the thread
- You MUST offer the stated defaults for items 9 and 10 rather than blocking on them, and You MUST say the default out loud, because most customers have not decided permissions or evaluation policy and do not need to in order to see their workflow run — but a default nobody heard is an assumption
- You MUST NOT default items 1 to 8 silently, because each one changes the SHAPE of what gets built, so a wrong guess there is work the customer has to unpick rather than a setting they flip
- You MUST tell the customer which of the things they volunteered are not needed yet — model choice, token budgets, dedicated runtimes, long-term memory, cost — because otherwise they spend the session on settings that have working defaults
- You SHOULD ask the one question that is not in the config — "when this goes wrong, who finds out and how?" — because the answer decides where the gates belong
- You MUST restate the complete requirement set as a numbered list and get explicit confirmation before proceeding, because everything downstream derives from it
- Validation: all ten items are either answered or carry a default the customer has seen, and the customer has confirmed the restatement
- On failure: ask again for the specific items still unanswered. You MUST NOT proceed with an item unresolved, because the cost of guessing is discovered three steps later when the topology is already written

### 1. Load the framework contract

Read the authoritative definitions of what may appear in `app/workflow.json` before
proposing anything, so the design is constrained by the schema rather than by memory.

**Constraints:**
- You MUST read `orchestrator/app/keys.json`, which is where every legal key and its default is authored
- You MUST read `orchestrator/docs/WORKFLOW_REFERENCE.md` for what reads each key
- You MUST read the shipped `orchestrator/app/workflow.json` as the worked example of every construct
- You MUST NOT read `orchestrator/app/workflow.schema.json` into context because it is a 106 KB generated projection of `keys.json` and will consume the context you need for authoring
- You MUST record the seven legal tool `type` values and their required keys before continuing
- Validation: You MUST confirm you can state, without guessing, which keys are required for each of the seven tool types
- On failure: hard stop. You MUST NOT invent configuration keys, because an unknown key fails at `terraform plan` or `cdk synth` and the customer will read that as the framework being broken

### 2. Design the topology and confirm it with the user

Convert the confirmed requirement set from step 0 into stages, agents, gates and branches,
then get agreement before writing any files.

**Constraints:**
- You MUST design only from items the customer confirmed in step 0, and You MUST NOT introduce a stage, gate or branch that answers no checklist item, because an unrequested stage is one the customer has to discover and remove
- You MUST express the design as an ordered list of stages, where each stage is one of: a single `agent`, a `parallel` group, or a `sequence`
- You MUST use `parallel` for agents that do not read each other's output, because a parallel stage is the only place the framework offers a subset re-run
- You MUST place a `hitl` gate wherever **review_points** requires human approval, and You MUST give every `parallel` or `sequence` gate both a `gateId` and a `gateName`
- You MUST assign each agent a `produces` value drawn from **domain_vocabulary**, not from this sample's vocabulary
- You MUST propose `runtime: "main"` for every agent unless the customer needs separate scaling or isolation, because a `dedicated` runtime is another AgentCore Runtime to pay for and deploy
- You MUST present the design as a short numbered list and ask the user to confirm or correct it
- You MUST NOT write any file until the user confirms, because every later step derives from this shape and reworking it after the agent folders exist wastes their time
- Validation: the design is confirmed by the user
- On failure: revise and re-present. You MUST NOT proceed on an unconfirmed design, because every later step derives from it and the agent folders would have to be rewritten

### 3. Clear the sample out of the way, and prepare a Python environment

The repository ships a nine-agent AWS-architecture workflow. A new use case replaces it,
and nothing later in this SOP works until it is gone.

**Constraints:**
- You MUST run `python3 scaffold.py reset --dry-run` and show the user what it will remove, then `python3 scaffold.py reset`, because it clears `agents`, `steps`, `tools`, the agent folders, the tool folders and the sample KB corpora in one operation and leaves a workflow that still passes the suite
- You MUST NOT clear those by hand, because `app/subagents/`, `app/tools/` and `workflow.json` must agree in BOTH directions and a single leftover folder fails a test whose message is about the framework rather than about the leftover
- You MUST pass `--keep-kb` only when the customer is genuinely reusing this sample's AWS reference documents, because every top-level folder in `kb_docs/` is ingested and they would otherwise pay to index notes they will never query
- You MUST treat the `first_agent` it leaves behind as scaffolding: rename it to the customer's first real agent or delete it once their own agents exist
- You MUST create a Python environment before relying on any gate, because the suite needs `langgraph`, `pydantic` and `boto3` and a bare `python3 -m pytest` fails at collection with `ModuleNotFoundError`:
  `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt -r requirements-dev.txt`
- You SHOULD keep `app/subagents/_shared/contracts/` initially and replace its asset shapes as you write the new agents, because they are the worked example of a well-formed asset
- Validation: `.venv/bin/python -m pytest` passes immediately after the reset. It is meant to — that green suite is the customer's safety net for every step that follows
- On failure: hard stop, because a reset that leaves the suite red means the repository was already inconsistent and nothing later can be trusted

### 4. Declare the tools

Write the `tools` block for every entry in **data_sources**. This is configuration only —
no IaC, no IAM, no Cedar policy.

**Constraints:**
- You MUST use a tool key matching `^[A-Za-z][A-Za-z0-9]*$` — camelCase, no underscores or hyphens — because the key builds both the Gateway target name, which allows no underscores, and the Cedar policy name `permit_<key>`, which allows no hyphens, so neither separator survives both. You MUST NOT apply this rule to agent ids, because those may contain underscores and `cost_research` is legal
- You MUST choose the `type` by how the source is reached: `kb` for Bedrock Knowledge Base corpora, `mcp` for an existing MCP endpoint, `openapi` for a REST API you have a spec for, `lambda` for anything else — a warehouse, an RDBMS, a VPC resource, a control-plane API
- You MUST treat `lambda` as the escape hatch and say so to the user when a source fits no other type, because the five types are framework code and adding a sixth would mean editing seven files across both IaC paths
- You MUST supply `rowFields` for any `lambda` or `openapi` tool whose result is tabular, so agents read rows by ROLE rather than by the source's field names
- You MUST declare a customer's own Lambda tool with `lambdaArn`, NOT with `source`, because `source` is closed by `builtinLambdaSource` in `app/vocabulary.json` to the single folder the repo ships — a framework-deployed function needs an execution role config cannot express, and the shipped role grants only logs plus read-only on the public AWS price list. With `lambdaArn` the customer deploys and owns the function and the framework registers it as a Gateway target
- You MUST NOT widen `builtinLambdaSource` to make a customer's `source` validate, because that is a framework-owned file and the deploy would then create a function with a role that cannot reach their data
- You MUST write an `openapi` tool's spec to `orchestrator/app/tools/<source>/openapi.json`, because `source` for `type: "openapi"` is deliberately open — the framework only uploads a file, which needs no permissions
- You MUST write `toolSchema` as an ARRAY of tool descriptors, each `{name, description, properties}` with `type`, `required` and `description` on every property, because it is not a JSON Schema object and a `{"type": "object", "properties": …}` value fails schema validation with "is not of type 'array'"
- You MUST copy the customer's documents to `orchestrator/kb_docs/<corpus>/` for a `kb` tool, where each top-level folder becomes one corpus
- You MUST NOT write a Lambda ARN, IAM policy, Gateway target or Cedar policy anywhere, because all four are generated from this block and a hand-written one will be overwritten or will conflict
- Validation: You MUST run `python3 build_schema.py --check` and `python3 format_workflow.py --check` from `orchestrator/`
- On failure: retry with the error. A schema error names the offending key

### 5. Scaffold the agent packages

Create each agent's folder and its `workflow.json` entry together, using the shipped
script rather than writing files by hand.

**Constraints:**
- You MUST use `python3 scaffold.py agent <agent_id>` from `orchestrator/`, because it writes the config entry and the folder as one operation and they cannot drift
- You MUST pass the flags the design calls for: `--produces`, `--runtime {main,dedicated}`, `--max-tokens`, `--tool <tool_key>`, and `--remote --skill <skill>` for an agent you do not operate
- You MUST run it once with `--dry-run` first and show the user what it will write
- You MUST NOT hand-write `app/subagents/<id>/__init__.py`, `agent.py` or `prompts.py` skeletons, because scaffold.py already emits the `from .agent import agent` wiring the loader requires and a hand-written package that omits it fails at import
- You MUST use the agent id as the folder name, since the framework derives one from the other
- You MUST add an `agentcore.evaluations` block to at least one agent yourself, because `scaffold.py` does not write one and `tests/test_evaluations_gate.py::test_the_shipped_workflow_still_has_evaluable_agents` fails when no agent is evaluable. Use `{"enabled": true, "auto": false, "evaluators": ["Builtin.Faithfulness", "Builtin.ResponseRelevance"]}` on the agents whose output quality matters, and `auto: true` on the final deliverable so it is scored at run completion
- Validation: You MUST confirm `orchestrator/app/subagents/<id>/` exists with all three files for every non-remote agent, and that `python3 -c "import app.subagents.<id>"` succeeds
- On failure: hard stop and report which agent failed to import

### 6. Write the prompts and the agent logic

Fill in each agent's `prompts.py` and `agent.py` so it produces the customer's asset type.

**Constraints:**
- You MUST implement `async def run(self, ctx: AgentContext) -> str` returning the asset as a JSON string
- You MUST reach every external capability through `ctx` and no other way, because `ctx` is where cost metering, token counting, guardrails, OTEL spans and policy checks are applied — a direct `boto3` call bypasses all of it and the run will show no cost, no prompt and no evaluation. The available calls are: `ctx.llm(system, user, model, max_tokens, name)`, `ctx.call_tool(tool_key, query)`, `ctx.call_tool_rows(tool_key, query)`, `ctx.retrieve(query, doc_type)`, `ctx.input(agent_id)`, `ctx.memory_recall(query)`, `ctx.memory_store(content)`, `ctx.guardrail(text, source)`, `ctx.get_identity_token(provider)`, `ctx.log(msg)`, `ctx.heartbeat(pct)`
- You MUST keep arithmetic in Python and judgment in the prompt, because a model asked to total figures will produce a plausible wrong number and a reviewer cannot tell
- You MUST NOT let an agent state a figure that no upstream asset or tool result carries, because `app/common/grounding.py` flags ungrounded figures on the run timeline and the run will be sent back
- You MUST NOT fabricate a fallback value when a tool or model call fails, because the framework deliberately raises `ToolUnavailable` and `ModelUnavailable` so the run fails with a reason attached to the failing agent
- You SHOULD define the asset shape in `app/subagents/_shared/contracts/` when more than one agent produces or reads it
- Validation: You MUST run `ruff check .` and `python3 -m pytest` from `orchestrator/`
- On failure: retry with the error

### 7. Wire the stages, gates and access rules

Complete the remaining `workflow.json` blocks so the run, the review gates and the UI
reflect the confirmed design.

**Constraints:**
- You MUST write `steps` exactly as confirmed in step 2, with `hitl`, `gateId` and `gateName` where the design places gates
- You MUST set `ui.title` and `ui.heading` to the customer's product name, because those two keys drive the browser tab, the top navigation, the side navigation, the breadcrumb and the info panel
- You MUST set `ui.defaultTopic`, `ui.topicPlaceholder` and the assistant strings to the customer's wording, because a `ui` key nothing renders fails `tests/test_config_keys.py`
- You MUST set `authorization` to the customer's identity-provider groups for the actions they want restricted, and You MUST tell them the UI only hides controls while `bff/authz.py` enforces them again server-side
- You SHOULD add a `branch` to a stage only where the customer states a genuine conditional, because the graph can draw the configured order but a branch's real path depends on output
- Validation: You MUST run `python3 format_workflow.py` then `python3 format_workflow.py --check` and `python3 build_schema.py --check`
- On failure: retry with the error

### 8. Run every gate and report

Prove the deployment is buildable before telling the user it is ready.

**Constraints:**
- You MUST run all of these and report each result: `python3 -m pytest`, `ruff check .`, `python3 format_workflow.py --check`, `python3 build_schema.py --check` from `orchestrator/`; `npx tsc --noEmit && npx vitest run && npm run build` from `orchestrator/web`; `npx tsc --noEmit -p . && npx jest` from `orchestrator/cdk`; `terraform fmt -check -recursive` from `orchestrator/terraform`
- You MUST NOT report success on any gate you did not actually run, because a green summary over an unrun suite is worse than no summary
- You MUST fix every failure and re-run, rather than reporting the failure as a known issue (except the sample-convention tests on the applied-bundle path above), because the test suite derives its expectations from the customer's own `workflow.json` and a failure means their config is genuinely wrong
- You MUST state plainly that no deployment has happened and name the next command — `terraform apply` or `cdk deploy` — because the gates prove the config is valid, not that it runs
- ⚠️ MANDATORY OUTPUT STEP: You MUST list the four surfaces you changed with file paths, so the customer can review exactly what they now own
- Validation: every gate passes
- On failure: hard stop and report which gate failed and why

## Examples

### Example 1: Insurance claims settlement

**Input:**
- use_case_description: "Settle household claims: read the FNOL, check policy wording, price the repair, produce a settlement decision a human approves."
- domain_vocabulary: "fnol-summary, coverage-finding, repair-estimate, settlement-decision"
- data_sources: "policy wordings as KB docs; parts pricing via a Lambda"
- review_points: "one gate on the research group, one before the settlement is issued"

**Expected Behavior:**
Proposes four stages — `intake`, a parallel research group gated for review, an
`adjust` agent, then `settle` gated for approval. Declares a `kb` tool and a `lambda`
tool, copies the wordings into `kb_docs/policy/`, writes
`app/tools/partsPricing/handler.py`, scaffolds four agent packages, then runs all gates.

### Example 2: Reasoning-only workflow, no external data

**Input:**
- use_case_description: "Review an architecture proposal against our internal standards and produce a decision record."
- domain_vocabulary: "proposal-summary, standards-finding, decision-record"

**Expected Behavior:**
Touches two surfaces only — `workflow.json` and three agent folders. Declares no
`tools` block, writes nothing to `app/tools/` or `kb_docs/`, and says so explicitly.

## Troubleshooting

### `terraform plan` or `cdk synth` rejects a key
The key is not in `app/keys.json`. Run `python3 build_schema.py --check`; the error names
the offending entry. Do not add the key to the schema to make it pass — the schema is
generated, and a key nothing reads is a key that does nothing.

### A tool key is rejected
Tool keys must match `^[A-Za-z][A-Za-z0-9]*$`. Underscores and hyphens both fail, because
the key becomes a Gateway target name (no underscores) and a Cedar policy name
`permit_<key>` (no hyphens). Use `claimsHistory`, not `claims_history`. Agent ids are not
restricted this way.

### An agent import fails after scaffolding
`app/subagents/<id>/__init__.py` must contain `from .agent import agent`. Re-run
`scaffold.py` rather than patching by hand.

### The run shows no cost, prompt or evaluation for an agent
That agent is calling a model or a service directly instead of through `ctx`. Every
external call must go through `ctx`, which is where metering, guardrails and spans are
applied.

### A figure is flagged on the timeline
`app/common/grounding.py` found a number in the output that appears in no upstream asset
and in no tool result. Either cite the source or remove the figure. Agents bound to a
`tool` are exempt, because their figures come from the tool.
